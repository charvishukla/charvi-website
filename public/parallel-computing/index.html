1. Matrix Multiplication with ARM SVE

Single-core double-precision GEMM on AWS Graviton

We wrote a cache-blocked DGEMM in the style of BLIS. The matrices are split into large tiles that fit in the L2 and L3 caches (MC=256, KC=128, NC=256). Each tile is packed into contiguous memory so the kernel reads it in order. A macro-kernel then hands each pair of packed sub-panels to a micro-kernel written with ARM SVE intrinsics.

  • Micro-kernel: computes an 8×8 block of C held entirely in vector registers. It runs in two half-passes that match the 4-double vector length, broadcasting values of A against loaded rows of B with fused multiply-adds.
  • Edge cases: leftover rows go through smaller 4-, 2- and 1-row versions of the kernel. Leftover columns use SVE predicates to mask out invalid lanes, so the kernel never reads or writes out of bounds.
  • Profiling: we used perf hardware counters to explain the dips in performance. For example, going from N=512 to N=513 adds about 9M L1 and 1.7M L2 cache refills because of the partial panels.

2. Matrix Multiplication in CUDA

Single-precision GEMM on an NVIDIA T4 GPU

Each 16×16 block of 256 threads computes one 64×64 tile of C. The block loads tiles of A and B into shared memory, and neighboring threads read neighboring addresses so global-memory loads coalesce. Each thread then keeps a 4×4 block of C in registers, which gives it 16 independent accumulators (instruction-level parallelism). The inner loops are fully unrolled.

  • Two load paths: when N divides evenly into tiles, loads skip bounds checks entirely. Otherwise, partial tiles are padded with zeros, so the compute loop stays the same for every N.
  • What didn't work: double-buffered software pipelining went over the shared-memory budget at our tile sizes.
  • Roofline: the T4's theoretical peak is 7.68 TFLOP/s. At N=2048 the arithmetic intensity is about 341 FLOP/byte, far into the compute-bound region, and our kernel reaches 3.30 TFLOP/s, about 42% of peak.

3. Distributed 2D Wave Simulation with MPI

5-point stencil wave solver on SDSC Expanse

The solver advances the 2D wave equation with a 5-point stencil and absorbing boundary conditions. The grid is split across a 2D Cartesian grid of MPI processes (MPI_Cart_create), and no process gets more than one extra row or column of work than any other.

  • Ghost-cell exchange: each step uses non-blocking MPI_Isend/MPI_Irecv. A strided MPI_Type_vector sends columns, which aren't contiguous in memory, without manual packing.
  • Overlapping communication and compute: after posting the exchange, each process updates interior cells that don't depend on ghost cells, then waits and finishes the edge ring.
  • Boundaries: absorbing boundary conditions are applied only on processes that sit on the global edge of the grid.

Process geometry matters

With the same 256 processes, the shape of the process grid changed throughput by 30%. C++ stores the grid row by row, so north–south ghost rows are contiguous while east–west ghost columns are strided and slower to send. Layouts that keep the strided edge short won, even over the square layout that minimizes total communication.
